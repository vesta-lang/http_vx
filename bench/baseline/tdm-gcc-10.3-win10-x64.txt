  serving (tdm-gcc-10.3-win10-x64)
    requests per round                      900
    requests per second                 2369668
    per request                             422 ns

    NO system calls: the backend hands the bytes over from
    memory.  This is the cost of the HTTP machinery alone.
    Over a socket, one read and one write cost more than all
    of it together -- which is why what is counted above is
    HOW MANY of them, not how long.

  system calls per request (tdm-gcc-10.3-win10-x64) -- R15
    notices                                1.00
    reads                                  1.00
    writes                                 1.00
    a simple request: one notice, one read and one write.
    The notice is what buys R1 -- without it an idle
    connection would hold a buffer -- and a PIPELINED
    request does not pay it, because its bytes are here.

    the ratio for the LARGE head must be LOWER than or
    equal to the one for the small head.  If it is higher,
    the parser starts over, and that is quadratic against
    somebody sending a request a byte at a time on purpose.

  memory per connection (tdm-gcc-10.3-win10-x64)
    hot record                               24 B
    cold record                              56 B
    deadline + free slot                     16 B
    FIXED PER CONNECTION                     96 B
    one million connections                91.6 MB
    bytes held in the pool                    0 B

    connections adopted 1024, buffers lent 0
    an idle connection holds NO buffer: the read is asked
    for in two halves, and the first -- "tell me when there
    is something" -- names none.  It is the zero-byte
    receive on Windows and the watched descriptor on epoll.
    What bounds the pool is the ANSWERS in flight, not the
    connections open.
